# P4.3 — Separate platform delivery and state ownership

_Part of the [delivery roadmap](../ROADMAP.md)._

- [x] **Task 1.** After a working staging extraction, move platform configuration/delivery
      into a dedicated platform repository. Keep immutable service-specific
      application artifacts, narrow OIDC roles, previous-contract compatibility,
      and Phase 3 affected-workspace improvements.
- [x] **Task 2.** Inventory the four Terraform roots (`bootstrap`, `development`,
      `environment`, `production`), backend keys, locks, IAM trust, configuration,
      and owning workflows. Close #9/#10 before any ownership transfer.
- [x] **Task 3.** Rehearse development first: freeze the old writer, back up/version state,
      transfer configuration/workflow authority, verify an unchanged plan against
      the existing backend, then enable exactly one new writer. Transfer remaining
      roots individually with the same verification and rollback instructions.
      Do not recreate resources or create competing state authorities. Recover
      locks only with verified ownership and no active apply.
- [ ] **Task 4.** Demonstrate independent service delivery, scaling, health, migration,
      rollback, and activation/deactivation in staging. Keep production rehearsal
      gated on the unresolved Phase 2 issues.

Exit: evidence identifies one authorized writer per root, unchanged resource
identity, no unexpected replacements, and a rehearsed transfer rollback. A
service-only release builds/deploys/rolls back without rebuilding unrelated
services. Record gated production demonstrations as outstanding.

- **Independent service delivery (issue #19 item 3) — fixed and verified
  live, twice.** Root cause confirmed as suspected: `deploy-staging.yml`
  resolved web/worker/discovery images from one shared `commit_sha` input.
  Fixed in `vinylhound-platform@d35b591`: optional
  `web_commit_sha`/`worker_commit_sha`/`discovery_commit_sha` inputs
  override `commit_sha` per service, and `infra/terraform/environment`'s
  `DEPLOYMENT_VERSION` env var — previously one shared Terraform variable
  feeding all three task definitions' `common_environment` local — is now
  three independent variables
  (`web_deployment_version`/`worker_deployment_version`/
  `discovery_deployment_version`), each set directly on its own task
  definition. Without that second change, a discovery-only redeploy would
  still have bumped web/worker's task definition revision (same image, new
  env var) and forced an unrelated rollout — the env-var sharing was as
  real a coupling as the image-resolution one.

  Verified with two real `deploy-staging.yml` dispatches (full
  activate/deploy/deactivate cycles), not just a plan: pushed a trivial
  discovery-only commit ([`4e8112b`](https://github.com/jessig1/vinylhound_new/commit/4e8112bbbcbfc340ac623d6f116d93d9ba0fde2f)),
  deployed it with `discovery_commit_sha` at that commit while
  `web_commit_sha`/`worker_commit_sha` stayed pinned to the
  previously-deployed commit. Confirmed via `aws ecs describe-task-definition`
  that web's and worker's deployed image **digest** never changed across
  both runs, byte-identical before and after, while discovery's changed to
  the new commit's image. Web/worker's task definition _revision number_
  still incremented each run — traced this down to an unrelated, unavoidable
  mechanism: staging's task definitions are destroyed and recreated on every
  activate/deactivate cycle (`active_count` gated on `environment_active`),
  so a new revision number happens regardless of content; the container
  definitions themselves were diffed and confirmed byte-identical across
  revisions. Commented on [issue #19](https://github.com/jessig1/vinylhound_new/issues/19)
  with the full before/after digest evidence.
