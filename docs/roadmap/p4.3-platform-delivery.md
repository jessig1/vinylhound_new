# P4.3 — Separate platform delivery and state ownership

_Part of the [delivery roadmap](../ROADMAP.md)._

- [x] **Task 1.** After a working staging extraction, move platform configuration/delivery
      into a dedicated platform repository. Keep immutable service-specific
      application artifacts, narrow OIDC roles, previous-contract compatibility,
      and Phase 3 affected-workspace improvements.
- [x] **Task 2.** Inventory the four Terraform roots (`bootstrap`, `development`,
      `environment`, `production`), backend keys, locks, IAM trust, configuration,
      and owning workflows. Close #9/#10 before any ownership transfer.
- [ ] **Task 3.** Rehearse development first: freeze the old writer, back up/version state,
      transfer configuration/workflow authority, verify an unchanged plan against
      the existing backend, then enable exactly one new writer. Transfer remaining
      roots individually with the same verification and rollback instructions.
      Do not recreate resources or create competing state authorities. Recover
      locks only with verified ownership and no active apply.
- [ ] **Task 4.** Demonstrate independent service delivery, scaling, health, migration,
      rollback, and activation/deactivation in staging. Keep production rehearsal
      gated on the unresolved Phase 2 issues.

Exit: evidence identifies one authorized writer per root, unchanged resource
identity, no unexpected replacements, and a rehearsed transfer rollback. A
service-only release builds/deploys/rolls back without rebuilding unrelated
services. Record gated production demonstrations as outstanding.

  **Three real, previously-undetected bugs were found and fixed while
  getting the real deploy to succeed** — none by inspection, all by
  actually running the pipeline against real AWS for the first time:
  1. My own first cut of `deploy-staging.yml` tried to build Docker images
     inside the platform repository's own checkout, which has no
     `Dockerfile.web` (no application source, by design) — the same
     mistake development's transfer had correctly avoided. Fixed by adding
     `build-staging-images.yml` to `vinylhound_new` (mirroring
     `build-development-images.yml`, using the narrow
     `vinylhound-github-ecr-push` role) and having `deploy-staging.yml`
     require the `${sha}-staging` images to already exist.
  2. The shared deploy-role policy (`local.deploy_actions` in
     `infra/terraform/bootstrap/main.tf`) was missing `servicediscovery:*`,
     needed for the discovery service's ECS Service Connect namespace — the
     real reason issue #19's own staging rehearsal had never succeeded.
     Fixed and applied to real AWS (all three environments' deploy roles
     share this policy).
  3. `scripts/aws/run-worker-command.sh`'s ECS `containerOverrides` (and
     `deactivate-environment.yml`'s `kubectl exec` drain-check) were both
     missing `--experimental-transform-types` — an override replaces the
     image's own `CMD` entirely rather than appending to it, silently
     dropping the flag `Dockerfile.worker`'s `CMD` carries for exactly this
     reason (cross-package `.ts` resolution through non-erasable
     constructor parameter properties). This had never been exercised
     against a real image before; found via staging's own first-ever real
     `migrate` invocation crashing with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`.
     Also fixed `GITHUB_SHA`/`${{ github.sha }}` resolving to the platform
     repository's own commit rather than the application repository's — a
     reserved GitHub Actions name that cannot be overridden via `env:`, so
     `deploy-staging.yml` now takes an explicit `commit_sha` input
     (matching `deploy-development.yml`'s own pattern) and uses
     `DEPLOY_COMMIT_SHA` instead.

here:

- **Activation/deactivation**: demonstrated via a real
  `deploy-staging.yml` cycle, confirmed inactive afterward via both
  `terraform output` and the SSM activation parameter's absence.
- **Migration**: migrations `021`/`022` re-ran with zero drift, confirming
  idempotency (already applied from Task 3).
- **Health**: `/api/healthz`/`/api/readyz` confirmed repeatedly against the
  live URL; the full authenticated scan → confirm → library pipeline smoke
  test (issue #29 item 3) was not completed — minting a real Clerk session
  programmatically needs the Clerk secret key, which this session's
  credential-handling guardrail blocked outright.
- **A real, previously-undetected bug found and fixed live**: `worker` was
  crash-looping on every deployment (including Task 3's own prior runs,
  confirmed from an earlier log stream), invisible to
  `aws ecs wait services-stable` because that check only compares task
  count, not container health history. Root cause: a plain ECS-managed
  `volume{}` `/tmp` bind mount defaults to root ownership, unwritable by
  the non-root `USER 1000:1000` every service's Dockerfile runs as; only
  `worker`'s health check (a heartbeat file write) ever exercised this.
  Fixed in `vinylhound-platform` (`6d78755`) by switching all three
  services to a Linux `tmpfs` mount instead; verified live with a second
  real deploy (`RUNNING`/`HEALTHY`, zero failed tasks, zero heartbeat
  failures).
- **Independent service delivery** (issue #19 item 3): a discovery-only
  commit was pushed and deployed, surfacing a real gap instead of proving
  the criterion — `build-staging-images.yml` rebuilds all three images per
  commit regardless of what changed, and `deploy-staging.yml` resolves all
  three services from one `commit_sha` input, so there is currently no way
  to redeploy discovery alone through the real pipeline. Not fixed this
  session (would need either reproducible per-service builds or a
  multi-commit-input redesign of the deploy workflow).
- **Scaling** (issue #19 item 4): not demonstrated. `enable_execute_command`
  was added to `web` and verified reachable, but the local
  `session-manager-plugin` install this session needed couldn't complete
  non-interactively, and staging's discovery service reports
  `discoveryConfigured: false` (no real MusicBrainz/Spotify credentials
  configured) — moot regardless of the exec blocker, since the exercise
  would only reach the not-configured error path. Both temporary additions
  (`hold_minutes`, `enable_execute_command`) were reverted (`7c7c85a`)
  after use.
- **Rollback**: not attempted. The migration `021`/`022` rollback rehearsal
  against staging's real Aurora cluster (issue #29 item 4) is this task's
  highest-risk remaining item.
