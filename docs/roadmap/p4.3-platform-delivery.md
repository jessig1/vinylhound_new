# P4.3 — Separate platform delivery and state ownership

_Part of the [delivery roadmap](../ROADMAP.md)._

- [x] **Task 1.** After a working staging extraction, move platform configuration/delivery
      into a dedicated platform repository. Keep immutable service-specific
      application artifacts, narrow OIDC roles, previous-contract compatibility,
      and Phase 3 affected-workspace improvements.
- [x] **Task 2.** Inventory the four Terraform roots (`bootstrap`, `development`,
      `environment`, `production`), backend keys, locks, IAM trust, configuration,
      and owning workflows. Close #9/#10 before any ownership transfer.
- [ ] **Task 3.** Rehearse development first: freeze the old writer, back up/version state,
      transfer configuration/workflow authority, verify an unchanged plan against
      the existing backend, then enable exactly one new writer. Transfer remaining
      roots individually with the same verification and rollback instructions.
      Do not recreate resources or create competing state authorities. Recover
      locks only with verified ownership and no active apply.
- [ ] **Task 4.** Demonstrate independent service delivery, scaling, health, migration,
      rollback, and activation/deactivation in staging. Keep production rehearsal
      gated on the unresolved Phase 2 issues.

Exit: evidence identifies one authorized writer per root, unchanged resource
identity, no unexpected replacements, and a rehearsed transfer rollback. A
service-only release builds/deploys/rolls back without rebuilding unrelated
services. Record gated production demonstrations as outstanding.

**Task 3, in progress as of 2026-09-23: `development` and `environment`
(staging) have both been transferred and verified live; `production`/
`bootstrap` have not.** At the maintainer's explicit direction ("work on
task 3", then "finish up the remaining items", then "finish task 3"), and
their explicit choice (via AskUserQuestion) to close #9/#10 before any
ownership transfer:

- **#10 fixed**: `deactivate-environment.yml`'s `skip_activation_check`
  input previously skipped Kubernetes draining entirely; added a
  best-effort drain step (capped at 2.5 minutes, non-fatal) plus
  strengthened input descriptions documenting the real (and only) race
  window for `stale_lock_id`, and a new "Emergency production deactivation
  inputs" runbook in `docs/OPERATIONS.md`. Closed on GitHub with a comment
  summarizing the fix.
- **#9 fixed and applied to real AWS**: `aws_iam_role.github_deploy`'s
  `max_session_duration` is `14400` (verified live via `aws iam get-role`
  against all three deploy roles) with matching `role-duration-seconds` in
  the two affected workflows. Getting there surfaced and fixed a real,
  previously-unknown gap: `bootstrap` had no S3 backend and this checkout
  had no local state at all despite its real resources already existing in
  AWS (see `docs/HANDOFF.md`'s 2026-09-22 entries for the full `terraform
import` recovery). Rather than leave that fragility in place, bootstrap
  now has a real S3 backend (`infra/terraform/bootstrap/versions.tf`,
  bucket `vinylhound-tf`, key `bootstrap/terraform.tfstate`, native S3
  locking — the same mechanism the other three roots use); the imported
  local state was migrated in with `terraform init -migrate-state` and
  verified byte-identical (same 2-add/3-change/0-destroy plan before and
  after migration). The apply also created the `vinylhound-discovery` ECR
  repository, missing from the real account since before this session
  despite being in `bootstrap/main.tf`'s `for_each` since at least P4.1 —
  unrelated pre-existing drift, not a change this task intended. Closed on
  GitHub with a comment summarizing the fix.
- **`development`'s transfer to a new platform repository is done and
  live**: created [vinylhound-platform](https://github.com/jessig1/vinylhound-platform)
  (private, empty at creation); added ADR-0031's two-axis OIDC narrowing to
  `infra/terraform/bootstrap/main.tf` (a new narrow
  `vinylhound-github-ecr-push` role scoped to `ecr:*` on the four named
  repositories only, for the application repository's own image builds; the
  `development` deploy role's trust temporarily dual-trusted both
  repositories during rehearsal, then narrowed to the platform repository
  alone once the cutover was verified — single-writer discipline, applied
  in two separate, plan-verified Terraform applies); copied
  `infra/terraform/development` and a new `deploy-development.yml` (accepts
  a `repository_dispatch` or manual `workflow_dispatch`, with a `plan_only`
  rehearsal mode) into the new repository; **rehearsed first**: a plan-only
  dispatch against the real existing backend (`environments/development.tfstate`)
  using the exact live image digests returned **"No changes. Your
  infrastructure matches the configuration."**; only then froze the old
  writer (`gh workflow disable deploy-development.yml` in `vinylhound_new`,
  reversible); ran a real deploy from the platform repository (Terraform
  apply, secret-backed Lambda env injection, `npm run db:migrate` — "No
  migrations to run!", confirming no drift — and the smoke test), then
  independently verified `https://dev-vh.siliconforest.io/api/healthz`,
  `/api/readyz`, and `/` all return `200` directly, not just trusting the
  workflow's own smoke test. Added `build-development-images.yml` to
  `vinylhound_new` (using the new narrow ECR-push role) to keep building
  images on push to `main`, since the frozen `deploy-development.yml` was
  also the only thing doing that; it dispatches to the platform repository
  when a `PLATFORM_DISPATCH_TOKEN` secret is configured, and otherwise
  prints the exact manual `gh workflow run` command as a non-fatal
  fallback — the maintainer chose not to set up that token this session, so
  new pushes to `main` currently require a manual trigger of the platform
  repository's deploy workflow until it's added.
- **`environment` (staging)'s transfer is done and live — and, as a direct
  side effect, closed the substance of two long-stuck issues.** A prior,
  interrupted session had already applied step 1 (dual-trusting
  `vinylhound-github-staging-deploy` and `vinylhound-github-plan` for both
  repositories, committed as `p4.3.3`); this session resumed from there,
  verified that dual-trust live in AWS, and completed the rest: copied
  `infra/terraform/environment` and the `scripts/aws/*.sh` ops scripts
  `deploy-staging.yml` depends on (duplicated from `vinylhound_new` until
  `production` is also transferred) into the platform repository; added
  `platform.yml`'s `terraform-plan` job there, mirroring the app repo's own.
  **The first plan-only rehearsal did not show "no changes"** the way
  development's had — it showed 22 resources to add (the discovery service,
  scan/core database secrets, confirmation-processing queues), because
  staging's real infrastructure had never actually been updated for P4.1's
  discovery extraction or P4.2 Task 7's scan/core split, despite that code
  being in `main` for weeks (exactly what issues #19/#29 track). Asked the
  maintainer explicitly before proceeding; they chose to apply it as part
  of this cutover rather than defer it.

  **Three real, previously-undetected bugs were found and fixed while
  getting the real deploy to succeed** — none by inspection, all by
  actually running the pipeline against real AWS for the first time:
  1. My own first cut of `deploy-staging.yml` tried to build Docker images
     inside the platform repository's own checkout, which has no
     `Dockerfile.web` (no application source, by design) — the same
     mistake development's transfer had correctly avoided. Fixed by adding
     `build-staging-images.yml` to `vinylhound_new` (mirroring
     `build-development-images.yml`, using the narrow
     `vinylhound-github-ecr-push` role) and having `deploy-staging.yml`
     require the `${sha}-staging` images to already exist.
  2. The shared deploy-role policy (`local.deploy_actions` in
     `infra/terraform/bootstrap/main.tf`) was missing `servicediscovery:*`,
     needed for the discovery service's ECS Service Connect namespace — the
     real reason issue #19's own staging rehearsal had never succeeded.
     Fixed and applied to real AWS (all three environments' deploy roles
     share this policy).
  3. `scripts/aws/run-worker-command.sh`'s ECS `containerOverrides` (and
     `deactivate-environment.yml`'s `kubectl exec` drain-check) were both
     missing `--experimental-transform-types` — an override replaces the
     image's own `CMD` entirely rather than appending to it, silently
     dropping the flag `Dockerfile.worker`'s `CMD` carries for exactly this
     reason (cross-package `.ts` resolution through non-erasable
     constructor parameter properties). This had never been exercised
     against a real image before; found via staging's own first-ever real
     `migrate` invocation crashing with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`.
     Also fixed `GITHUB_SHA`/`${{ github.sha }}` resolving to the platform
     repository's own commit rather than the application repository's — a
     reserved GitHub Actions name that cannot be overridden via `env:`, so
     `deploy-staging.yml` now takes an explicit `commit_sha` input
     (matching `deploy-development.yml`'s own pattern) and uses
     `DEPLOY_COMMIT_SHA` instead.

  **The real cutover deploy then succeeded end to end**: `terraform apply`
  created the persistent foundation and the new discovery/scan/core/queue
  resources, `ensureDatabaseRoles` created the two new Postgres roles,
  migrations `021`/`022` applied cleanly against the real Aurora cluster

  `staging-passed-<sha>`, and staging deactivated cleanly afterward

  was a real activate/deploy/deactivate cycle, not a permanent change to
  staging's cost profile). Froze the old writer first

  `platform.yml`'s `terraform-plan` job there guarded with `false &&`) and
  narrowed `vinylhound-github-staging-deploy`'s trust to the platform
  repository alone once the cutover was verified — same single-writer
  discipline as `development`. Commented on issues
