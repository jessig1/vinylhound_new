# P4.2 — Extract scans and asynchronous confirmation

_Part of the [delivery roadmap](../ROADMAP.md)._

- [x] **Task 1.** Define scan ownership of scans/images/attempts/reviewed confirmations and
      core ownership of catalog/library/copies/favorites/playlists. Initially keep
      one physical PostgreSQL deployment with separate schemas and credentials,
      no cross-service table access, and a documented shared failure boundary.
- [x] **Task 2.** Generalize the outbox in a separate migration/refactor: aggregate type/ID,
      topic/version, dedupe key, correlation, and topic-aware dispatch. Remove the
      scan-only FK/topic CHECK and mandatory attempt-number assumption. Preserve
      skip-locked claiming, backoff, and replay safety; scope cancellation checks
      to analysis messages.
- [x] **Task 3.** Supersede ADR-0005 at cutover: one scan transaction stores the reviewed
      confirmation and versioned event. A core consumer atomically records an
      inbox dedupe receipt, catalog/library changes, and completion event; scan
      consumes completion into a projection. No cross-service dual writes.
- [x] **Task 4.** Specify same-key/same-payload replay and same-key/different-payload conflict.
      Duplicate delivery cannot create another physical copy; a genuinely new
      reviewed scan may. Show `Saving` until completion, then the stable library
      reference; expose delay/failure with safe retry and reconciliation.
- [x] **Task 5.** Isolate or fairly schedule confirmation dispatch so analysis cannot starve
      it. Set a confirmation-to-library latency target before implementation and
      include the existing outbox poller's delay in the measurement.
- [x] **Task 6.** Replace the cross-boundary confirmation/library restrict FK with explicit
      application invariants and durable audit references/projections. Record the
      policy in an ADR and preserve protected-history behavior unless explicitly
      changed. Make account export/deletion a durable, authenticated, retryable
      workflow; late events must not recreate deleted account data.
- [ ] **Task 7.** Use additive migrations, backfill, verification, then a single writer switch.
      Test rollback with in-flight events and reconciliation; never enable two
      authoritative writers. Deploy staging first, with gated EKS definitions
      and no extra development Lambdas.

Task 1 completed 2026-09-19 (ADR-0027), at the maintainer's direction to
start P4.2 Task 1 rather than wait on [issue #19](https://github.com/jessig1/vinylhound_new/issues/19)'s
still-open P4.1 live rehearsal — recorded here rather than silently skipped,
per `docs/ROADMAP.md`'s "Sequence and gates" note that P4.1 should precede
P4.2 with a proceed/defer decision at each boundary. No code changed: this
is a decision record, the same shape as P4.1 Task 1. `scan` owns `scans`,
`batches`, `image_assets`, `scan_attempts`, `scan_candidates`,
`scan_confirmations`, and `outbox_messages`; `core` owns `users`, `albums`,
`releases`, `catalog_references`, `library_items`, `library_copies`,
`playlists`, and `playlist_entries` — favorites needs no separate table
(ADR-0021's `library_items.favorited_at`). `users`' assignment to `core`
(unstated by this task's own text) is argued in the ADR: account lifecycle
is already core-shaped (ADR-0013/0014), and scan only ever needs to know
_which_ user a row belongs to, not to own the account. One physical
PostgreSQL deployment stays as-is; the decision is two Postgres schemas and
two least-privilege roles (`vinylhound_scan_app`/`vinylhound_core_app`)
replacing today's single undivided schema and single credential, with no
cross-schema `GRANT`. Eight existing foreign keys that will cross the new
line are named exactly in the ADR (`scans`/`batches`/`scan_confirmations`
→ `users`; `library_items`/`library_copies` → `scans`;
`scan_confirmations` → `releases` (ADR-0011's `restrict` FK) /
`library_items` / `library_copies`) and are explicitly left in place as a
documented, temporary exception — removing them is Task 3's and Task 6's
job, not this one's. The shared failure boundary is documented: one
Postgres instance and one migration history remain shared, and the engine
itself does not prevent a single transaction from crossing both schemas
until Task 7's physical writer cutover — today's `confirmScan` (ADR-0005)
and `deleteAccount` (ADR-0014) are cited as the exact transactions that
still do this. `docs/ARCHITECTURE.md` gained a matching "Scan and core
services" section. No schema, role, or migration exists yet; Task 7 creates
them as part of its own additive-migration/backfill/verify/single-writer
sequence.

Task 2 completed 2026-09-19 (ADR-0004 amendment): generalized
`outbox_messages` (migration `018_generalize_outbox.sql`) to resolve the four
scan-only constraints `docs/PHASE_3_4_PLAN_REVIEW.md`'s G8 named. Added an
`aggregate_type` column and dropped `aggregate_id`'s foreign key into
`scans` — existence/ownership of the named aggregate is now an application
invariant enforced by the producer transaction, the same pattern ADR-0027
already applies to the cross-schema FKs it names as a temporary exception.
Replaced the single-literal `topic` CHECK (`= 'scan.analyze.v1'`) with a
general `<aggregate>.<action>.v<N>` format CHECK matching
`packages/contracts/src/versioning.ts`'s `EVENT_TOPIC_PATTERN`. Made
`attempt_number` nullable (an analysis-specific retry counter; a
single-shot event like Task 3's confirmation event has none) and dropped the
`(topic, aggregate_id, attempt_number)` uniqueness constraint that stood in
as this table's dedupe key, since `idempotency_key`'s own uniqueness already
serves that purpose for every topic. Moved the dispatcher out of
`scan-repository.ts` into its own `packages/database/src/outbox-repository.ts`
module (G8's fourth item) and made it topic-aware: it claims the oldest
available row regardless of topic, looks up a publisher from a
caller-supplied topic-keyed registry, and parses the stored payload through
that topic's registered `EventContract` consumer schema (ADR-0022) when one
is registered, falling back to the raw payload for an unregistered topic.
`SELECT ... FOR UPDATE SKIP LOCKED` claiming, exponential backoff on publish
failure, and holding the row lock across the publish call are all
unchanged. The cancellation skip (a `canceled` scan's queued job is marked
published without delivery) is now scoped to the `scan.analyze.v1` topic
specifically — the only topic whose aggregate can be canceled between submit
and dispatch — rather than applying to every row regardless of topic.
Updated all three outbox-consuming call sites
(`apps/worker/src/index.ts`/`lambda.ts`/`e2e-worker.ts`) to pass a
single-entry registry for `scan.analyze.v1`; runtime behavior for that topic
is unchanged. Added an integration test proving the generalization directly:
a non-analysis-topic row naming a canceled scan as its aggregate is
dispatched normally (not skipped), a row naming an aggregate ID with no
owning table row at all is dispatched successfully (the FK is gone), and
`attempt_number` can be omitted. Verified locally: `lint`, `typecheck`,
`format:check --end-of-line auto`, `test` (403/403, unchanged count — no
tests moved suites), `test:integration` for `@vinylhound/database` (56/56,
+1 net new, run against a real Postgres migrated with the new file), and
`npm run build` (all workspaces). No ADR-0027 boundary changed: this task
operated entirely inside `scan`'s own schema, as ADR-0027's "Consequences"
section anticipated.

Task 3 completed 2026-09-19 (ADR-0028, superseding ADR-0005): replaced
`confirmScan`'s single transaction across scan and core tables with a
three-hop async pipeline, all still running inside today's one Postgres
database and one `apps/worker` process (physical separation stays Task 7's
job, per ADR-0027). Hop 1: `confirmScan` (`packages/database/src/
confirmation-repository.ts`) keeps its existing validation but now inserts
only a `pending` `scan_confirmations` row (new `status` enum;
`release_id`/`library_item_id`/`copy_id` null until completion;
`reviewed_release` widened to also carry `list`/`notes`/`copy`) and enqueues
a new `scan.confirmed.v1` event through the outbox Task 2 already
generalized for exactly this — zero changes needed to
`dispatchNextOutboxMessage` itself. Hop 2: new `processScanConfirmation`
(`confirmation-processing-repository.ts`) consumes that event and, in one
transaction, checks a new `confirmation_receipts` table (logically
core-owned per ADR-0027) by idempotency key — present means a duplicate
delivery, do nothing; absent means resolve the release
(`resolveReviewedRelease`, unchanged, still shared with `placeLibraryRelease`)
and write `library_items`/`library_copies` (moved unchanged from the old
`confirmScan`), then insert the receipt row, which plays both the inbox-
dedupe-guard role and the completion-event-to-dispatch role in one write.
Hop 3: new `dispatchNextConfirmationReceipt`
(`confirmation-receipt-repository.ts`, deliberately not sharing code with
`dispatchNextOutboxMessage` — single topic, no cancellation, no registry, a
genuinely simpler function) delivers a `confirmation.completed.v1` event that
new `applyConfirmationCompletion` (`confirmation-repository.ts`) projects
onto `scan_confirmations`, idempotently, flipping `status` to `completed`.
Found and fixed two correctness issues while rewriting `confirmScan`: the
`release` response object was built by spreading the whole (now widened)
`reviewedRelease` column, which would have leaked `list`/`notes`/`copy` past
`ConfirmedReleaseSchema.strict()` — fixed to build it from named fields; and
the existing "`libraryItemId === null` means removed-per-ADR-0018, delete and
allow reconfirmation" branch would have wrongly matched every `pending`
confirmation too — gated on `status === "completed"` as well, in both
`confirmScan` and `getScanConfirmationForUser`. Also found and fixed a real
FK bug before it shipped: `confirmation_receipts.library_item_id` was
initially modeled as `NOT NULL ... ON DELETE RESTRICT`, which would have
blocked the existing, unrelated "remove a saved record" feature (and account
deletion) once a completed confirmation existed for it; changed to nullable
`ON DELETE SET NULL`, matching `scan_confirmations`' own ADR-0018 pattern —
`payload` keeps the original ID for history regardless. New migration
`packages/database/migrations/019_supersede_scan_confirmation.sql`. Two new
event contracts (`packages/contracts/src/confirmation.ts`,
`scan.confirmed.v1` and `confirmation.completed.v1`, registered in
`events.ts`, fixtures added) and a widened `ScanConfirmationSummarySchema`
(`status`/`completedAt` as plain optional fields — no default — so the two
pre-existing frozen response fixtures, which have neither key, still
round-trip unchanged per ADR-0022's own doctrine; `release`/`libraryItem`
made nullable). `AccountExportConfirmationSchema.releaseId` also made
nullable for the same reason. `packages/queue/src/index.ts` generalized:
three topics now sharing one BullMQ-pair/SQS-pair shape justified factoring
`createBullMqTopicQueue`/`createBullMqTopicWorker` (+ SQS equivalents); the
existing `scan.analyze.v1` functions became thin wrappers with unchanged
external signatures. `apps/worker`'s `index.ts` and `e2e-worker.ts` gained a
second poll loop (`dispatchNextConfirmationReceipt`) and two more BullMQ/SQS
worker pairs; `lambda.ts` additionally gained routing of SQS records by
`eventSourceARN` across all three source queues, since one Lambda now serves
all three. The scan page's existing queued/processing poll loop
(`apps/web/src/app/scans/[scanId]/page.tsx`) now also polls while
`confirmation.status === "pending"` and shows a loading state instead of the
"Saved" card until `"completed"` — the minimal change needed to satisfy this
phase's own exit bar ("the UI never reports a completed save before the
completion projection arrives") without building Task 4's own "Saving…"
polish, retry affordances, or reconciliation UI. Designed via two parallel
Explore agents (worker/queue pipeline; confirm HTTP/UI flow) and one Plan
agent that read every touched file in full before implementation began; see
`docs/decisions/0028-async-scan-confirmation.md` for the full design and its
explicitly deferred gaps (Task 4/5/6/7, plus a documented account-deletion
race this pipeline inherits until Task 6).

Task 4 completed 2026-09-20/21 (ADR-0028 amendment): the replay/same-key-
conflict/duplicate-delivery-no-duplicate-copy semantics the roadmap text
names were already implemented and tested by Task 3 (`confirmScan`'s
idempotency-key/fingerprint compare; `processScanConfirmation`'s receipt
dedupe) -- this task's amendment to `docs/decisions/0028-async-scan-
confirmation.md` formalizes that with pointers to the exact tests proving
it, unchanged. What was genuinely new: a `pending` confirmation whose queue
delivery permanently fails (BullMQ exhausting its 5 attempts, an SQS
message dead-lettering) previously had no visible failure state and polled
forever. New `packages/database/src/confirmation-reconciliation-
repository.ts`'s `reconcileScanConfirmation` re-drives it by calling
`processScanConfirmation`/`applyConfirmationCompletion` directly off
durably stored data (the `scan.confirmed.v1` outbox row, the receipt's own
stored payload) rather than reaching into BullMQ/SQS -- rejected explicitly
because BullMQ won't re-run a job by re-adding its existing `jobId`, and SQS
has no per-message redrive, both of which would also mean maintaining
driver-specific retry code in `packages/queue`. This needed no new event
topic, schema enum value, or contract change. Found and fixed a real new
concurrency gap while building this: reconciliation calling
`processScanConfirmation` alongside the normal queue consumer can race on
the same event's receipt insert; fixed with the same
`pg_advisory_xact_lock` pattern `confirmScan` already uses, added as the
first statement in `processScanConfirmation`'s own transaction, and proven
under real concurrent calls by a new integration test. Two entry points:
`POST /api/v1/scans/:scanId/confirm/retry` (user-facing, surfaced in
`apps/web/src/app/scans/[scanId]/page.tsx` once a pending confirmation has
waited past a 20-second UX threshold -- not Task 5's formal latency
target) and a new worker sweep (`apps/worker/src/index.ts`, config
`CONFIRMATION_RECONCILIATION_POLL_INTERVAL_MS`/`_STALE_AFTER_MS`/
`_BATCH_SIZE`, defaulting to a 60-second poll and 5-minute staleness
threshold -- deliberately longer than the UI's own retry affordance, so a
user's click is the first line of recovery and the sweep is the safety net
for an unattended scan). Also fixed a small pre-existing UI bug found while
touching this page: the shared `LoadingState` component hardcoded the
kicker text "Scan in progress" even while rendering the confirmation-
pending state; it now takes a `kicker` prop. The known Task-6 gap (a
pending confirmation whose user was deleted mid-flight fails hop 2 with a
real FK violation) is unchanged -- reconciliation will retry it too, get
the same error, and it stays a real, visible failure; root-causing it is
still Task 6's job. Verified: `typecheck`/`lint`/`test` (417/417, +2 new
config-default tests); `test:integration` for `@vinylhound/database`
(68/68, +5 new: reconcile from a stuck-before-hop-2 state, from a stuck-
after-hop-2 state, a no-op on an already-completed confirmation, the new
concurrency test, and `listStalePendingConfirmations`' `olderThan`/`limit`
filtering); `npm run db:migrate` confirmed no schema change was needed;
`npm run build` (all workspaces, reverted the regenerated `next-env.d.ts`);
`format:check --end-of-line auto` (clean apart from the same pre-existing,
unrelated `apps/web/e2e/env.ts` warning this repository already carries);
the existing `apps/web/e2e/scan-flow.e2e.ts` suite against `mobile-
chromium` (6/6, confirming the confirm-and-save happy path and the kicker
fix still render correctly). A stuck/retry scenario was deliberately not
added to the e2e suite -- reliably simulating a dead-lettered queue job in
Playwright would be flaky; the new integration tests cover that logic
directly instead.

Task 5 completed 2026-09-21 (ADR-0028 amendment): fixed the starvation ADR-0028's
"Left to Task 5" note flagged -- `dispatchNextOutboxMessage`
(`packages/database/src/outbox-repository.ts`) claimed the single oldest
`outbox_messages` row _across every topic_, so `apps/worker`'s one combined
dispatch loop (registering both `scan.analyze.v1` and `scan.confirmed.v1`
publishers together) let a deep, continuously-replenished analysis backlog
delay a newer confirmation event with no bound. Chose isolation over weighted
fairness: `dispatchNextOutboxMessage` now scopes its claim query to
`Object.keys(publishers)` (an added `inArray(topic, ...)` filter, no schema
change needed since `SELECT ... FOR UPDATE SKIP LOCKED` already lets two
topic-scoped queries run against the same table without contending for each
other's rows), so a call site registering one topic can never claim, lock, or
back off a row of another. `apps/worker/src/index.ts`'s single dispatch loop
split into `dispatchAvailableAnalysisJobs` (`scan.analyze.v1` only, unchanged
`OUTBOX_POLL_INTERVAL_MS`) and `dispatchAvailableConfirmedEvents`
(`scan.confirmed.v1` only, new `CONFIRMATION_DISPATCH_POLL_INTERVAL_MS`,
default 200ms); `dispatchNextConfirmationReceipt`'s existing, already-isolated
hop 2 -> 3 loop also moved onto the new faster interval instead of reusing the
analysis one, since both confirmation hops share one latency budget.
`e2e-worker.ts` got the identical split; `lambda.ts`'s `dispatchOutbox` got
two topic-scoped passes (confirmed events first) instead of one combined pass.
Found and fixed a real, previously undetected bug while building this, not
just a missed optimization: a single-topic registry still competed for the
globally oldest row of _any_ topic under the old query, and on claiming one
outside its registry hit the "no publisher registered" branch -- the same
code path as a genuine delivery failure -- backing off an unrelated caller's
row under exponential backoff for no reason. `schema.integration.ts`'s
`dispatchUntil` helper had been doing exactly this to other tests'
`scan.confirmed.v1` rows throughout the suite; the topic-scoped query makes
this structurally impossible now.

Set the confirmation-to-library latency target _before_ this work, per the
roadmap text: p95 ≤ 2000ms, measured as `scan_confirmations.confirmedAt`
(hop 1's write) to `confirmation.completed.v1`'s `completedAt` (hop 2's
write, when `library_items`/`library_copies` become durable) -- which already
includes the hop 1 outbox poller's own pickup delay the roadmap text names.
Budgeted at a few hundred milliseconds nominal (≤200ms dispatch pickup +
tens of milliseconds each for BullMQ delivery and `processScanConfirmation`'s
transaction), with 2000ms as headroom for SQS's higher latency and ordinary
jitter -- a design budget, not a production measurement, since P4.1's live
staging rehearsal (issue #19) hasn't run yet and there is no real traffic to
sample from. Made it directly verifiable, not just estimated:
`applyConfirmationCompletion` (`packages/database/src/confirmation-
repository.ts`) now returns `{ latencyMs } | null` (null on its existing
redelivery/missing-row no-ops, computed from existing columns with no new
migration), logged as `confirmationToLibraryLatencyMs` on the worker's
existing `confirmation_completion_applied` line
(`apps/worker/src/confirmation-completion-handler.ts`). A real browser e2e
run (`apps/web/e2e/scan-flow.e2e.ts`, mobile-chromium) measured 165ms
end-to-end through real BullMQ/Postgres for the confirm-and-save test,
confirming the budget is realistic. Task 4's 20-second UI retry threshold and
5-minute reconciliation staleness threshold were revisited as its own resume
point asked and left unchanged: both remain well above this task's nominal
latency, so they still read as "something is actually wrong," not ordinary
pipeline delay. `infra/terraform/development`'s Lambda worker keeps its
pre-existing `rate(1 minute)` EventBridge outbox schedule untouched --
`docs/ROADMAP.md`'s own sequencing note places "additional development
service Lambdas" outside this scope, and staging/production run the
long-running process this task actually tuned -- but `dispatchOutbox` itself
still received the same topic-isolation fix. New config:
`CONFIRMATION_DISPATCH_POLL_INTERVAL_MS` (default 200ms, min 50ms,
`packages/config/src/index.ts`, `.env.example`). Verified: `lint`,
`typecheck`, `format:check --end-of-line auto` (clean apart from the same
pre-existing, unrelated `apps/web/e2e/env.ts` warning), `test` (419/419, +2
net new config-default tests), `test:integration` for `@vinylhound/database`
(69/69, +1 net new: proves a confirmed-event-only dispatcher never claims,
publishes, or backs off a pending, older analysis row and vice versa, using
real contract-valid rows from the existing scan-submission and
confirmation-request helpers already in the suite -- not a synthetic
unregistered topic, so it exercises the actual registered
`ScanConfirmedEventSchema`/`AnalyzeScanJobSchema` parse path too) and
`@vinylhound/storage`/`@vinylhound/queue`/`@vinylhound/worker` (unchanged),
`npm run build` (all workspaces, reverted the regenerated `next-env.d.ts`),
`npm run check:contracts` (passes, no contract changed), and the existing
`apps/web/e2e/scan-flow.e2e.ts` suite against `mobile-chromium` (6/6),
which is where the real 165ms measurement above came from. See ADR-0028's
2026-09-21 amendment for the full design and the isolation-vs-fairness
tradeoff.

Task 6 completed 2026-09-21 (ADR-0029): `scan_confirmations.release_id` and
`confirmation_receipts.release_id` changed from `restrict` to `set null`
(migration `020_account_deletion_workflow_and_release_id_policy.sql`) ahead
of Task 7, since a cross-schema `restrict` FK cannot survive the physical
split at all. No new runtime guard code was written -- no code path deletes a
`releases` row today (confirmed by search), and a completed confirmation's
`release_id` still cannot actually go null in practice: the existing
`scan_confirmations_status_consistency_check` already rejects that update, so
protected-history behavior for a completed confirmation is unchanged and
verified by a new integration test that asserts the rejection is now a
`23514` check violation, not the old `23503` FK violation.
`confirmation_receipts.release_id` now nulls instead of blocking, matching
its own already-`set null` `library_item_id`/`copy_id` siblings, with
`payload` preserving the resolved release id regardless -- also verified
directly. `deleteAccount` became a durable, drain-then-delete workflow:
`users` gained `deletion_requested_at`; a whole-account delete hard-deletes
immediately when zero `scan_confirmations` rows are `pending` (the common
case, byte-for-byte the same cascade as before), otherwise it durably records
the request and defers to a new background sweep
(`listAccountsReadyForDeletion`/`finalizeAccountDeletion`,
`ACCOUNT_DELETION_POLL_INTERVAL_MS`/`_BATCH_SIZE`, default 60s/50,
`apps/worker/src/index.ts`) that finalizes once every pending confirmation
drains via the existing Task 4 reconciliation mechanism. `confirmScan` now
refuses a new confirmation once deletion has been requested (`account_deleting`,
a new `DatabaseCommandErrorCode`, `409`), closing the inverse race; both
checks lock the same `users` row (`deleteAccount` `for("update")`,
`confirmScan`'s new check `for("share")`) so the two transactions serialize
correctly without new locking primitives. This makes the ADR-0028-documented
foreign-key violation (a `pending` confirmation whose user is deleted
mid-flight) provably unreachable, not merely retried more gracefully --
verified by a new integration test that drives a real pending confirmation
through both remaining pipeline hops _after_ calling `deleteAccount` and
observing `status: "pending"`, against a `users` row the test proves is still
present. `DeleteAccountResponseSchema` gained a required
`status: "deleted" | "pending"` field; the route and account-settings UI both
still work unchanged (any `2xx` response signs the user out) since the field
is additive. Verified: `lint`, `typecheck`, `format:check`, `test`
(422/422, +3 net new: two config-default tests, one contract round-trip
test), `docker compose up -d` + `npm run db:migrate`, `test:integration` for
`@vinylhound/database` (74/74, +5 net new, described above) and
