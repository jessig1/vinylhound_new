# P4.2 — Extract scans and asynchronous confirmation

_Part of the [delivery roadmap](../ROADMAP.md)._

- [x] **Task 1.** Define scan ownership of scans/images/attempts/reviewed confirmations and
      core ownership of catalog/library/copies/favorites/playlists. Initially keep
      one physical PostgreSQL deployment with separate schemas and credentials,
      no cross-service table access, and a documented shared failure boundary.
- [x] **Task 2.** Generalize the outbox in a separate migration/refactor: aggregate type/ID,
      topic/version, dedupe key, correlation, and topic-aware dispatch. Remove the
      scan-only FK/topic CHECK and mandatory attempt-number assumption. Preserve
      skip-locked claiming, backoff, and replay safety; scope cancellation checks
      to analysis messages.
- [ ] **Task 3.** Supersede ADR-0005 at cutover: one scan transaction stores the reviewed
      confirmation and versioned event. A core consumer atomically records an
      inbox dedupe receipt, catalog/library changes, and completion event; scan
      consumes completion into a projection. No cross-service dual writes.
- [ ] **Task 4.** Specify same-key/same-payload replay and same-key/different-payload conflict.
      Duplicate delivery cannot create another physical copy; a genuinely new
      reviewed scan may. Show `Saving` until completion, then the stable library
      reference; expose delay/failure with safe retry and reconciliation.
- [ ] **Task 5.** Isolate or fairly schedule confirmation dispatch so analysis cannot starve
      it. Set a confirmation-to-library latency target before implementation and
      include the existing outbox poller's delay in the measurement.
- [ ] **Task 6.** Replace the cross-boundary confirmation/library restrict FK with explicit
      application invariants and durable audit references/projections. Record the
      policy in an ADR and preserve protected-history behavior unless explicitly
      changed. Make account export/deletion a durable, authenticated, retryable
      workflow; late events must not recreate deleted account data.
- [ ] **Task 7.** Use additive migrations, backfill, verification, then a single writer switch.
      Test rollback with in-flight events and reconciliation; never enable two
      authoritative writers. Deploy staging first, with gated EKS definitions
      and no extra development Lambdas.

Task 1 completed 2026-09-19 (ADR-0027), at the maintainer's direction to
start P4.2 Task 1 rather than wait on [issue #19](https://github.com/jessig1/vinylhound_new/issues/19)'s
still-open P4.1 live rehearsal — recorded here rather than silently skipped,
per `docs/ROADMAP.md`'s "Sequence and gates" note that P4.1 should precede
P4.2 with a proceed/defer decision at each boundary. No code changed: this
is a decision record, the same shape as P4.1 Task 1. `scan` owns `scans`,
`batches`, `image_assets`, `scan_attempts`, `scan_candidates`,
`scan_confirmations`, and `outbox_messages`; `core` owns `users`, `albums`,
`releases`, `catalog_references`, `library_items`, `library_copies`,
`playlists`, and `playlist_entries` — favorites needs no separate table
(ADR-0021's `library_items.favorited_at`). `users`' assignment to `core`
(unstated by this task's own text) is argued in the ADR: account lifecycle
is already core-shaped (ADR-0013/0014), and scan only ever needs to know
_which_ user a row belongs to, not to own the account. One physical
PostgreSQL deployment stays as-is; the decision is two Postgres schemas and
two least-privilege roles (`vinylhound_scan_app`/`vinylhound_core_app`)
replacing today's single undivided schema and single credential, with no
cross-schema `GRANT`. Eight existing foreign keys that will cross the new
line are named exactly in the ADR (`scans`/`batches`/`scan_confirmations`
→ `users`; `library_items`/`library_copies` → `scans`;
`scan_confirmations` → `releases` (ADR-0011's `restrict` FK) /
`library_items` / `library_copies`) and are explicitly left in place as a
documented, temporary exception — removing them is Task 3's and Task 6's
job, not this one's. The shared failure boundary is documented: one
Postgres instance and one migration history remain shared, and the engine
itself does not prevent a single transaction from crossing both schemas
until Task 7's physical writer cutover — today's `confirmScan` (ADR-0005)
and `deleteAccount` (ADR-0014) are cited as the exact transactions that
still do this. `docs/ARCHITECTURE.md` gained a matching "Scan and core
services" section. No schema, role, or migration exists yet; Task 7 creates
them as part of its own additive-migration/backfill/verify/single-writer
sequence.

Task 2 completed 2026-09-19 (ADR-0004 amendment): generalized
`outbox_messages` (migration `018_generalize_outbox.sql`) to resolve the four
scan-only constraints `docs/PHASE_3_4_PLAN_REVIEW.md`'s G8 named. Added an
`aggregate_type` column and dropped `aggregate_id`'s foreign key into
`scans` — existence/ownership of the named aggregate is now an application
invariant enforced by the producer transaction, the same pattern ADR-0027
already applies to the cross-schema FKs it names as a temporary exception.
Replaced the single-literal `topic` CHECK (`= 'scan.analyze.v1'`) with a
general `<aggregate>.<action>.v<N>` format CHECK matching
`packages/contracts/src/versioning.ts`'s `EVENT_TOPIC_PATTERN`. Made
`attempt_number` nullable (an analysis-specific retry counter; a
single-shot event like Task 3's confirmation event has none) and dropped the
`(topic, aggregate_id, attempt_number)` uniqueness constraint that stood in
as this table's dedupe key, since `idempotency_key`'s own uniqueness already
serves that purpose for every topic. Moved the dispatcher out of
`scan-repository.ts` into its own `packages/database/src/outbox-repository.ts`
module (G8's fourth item) and made it topic-aware: it claims the oldest
available row regardless of topic, looks up a publisher from a
caller-supplied topic-keyed registry, and parses the stored payload through
that topic's registered `EventContract` consumer schema (ADR-0022) when one
is registered, falling back to the raw payload for an unregistered topic.
`SELECT ... FOR UPDATE SKIP LOCKED` claiming, exponential backoff on publish
failure, and holding the row lock across the publish call are all
unchanged. The cancellation skip (a `canceled` scan's queued job is marked
published without delivery) is now scoped to the `scan.analyze.v1` topic
specifically — the only topic whose aggregate can be canceled between submit
and dispatch — rather than applying to every row regardless of topic.
Updated all three outbox-consuming call sites
(`apps/worker/src/index.ts`/`lambda.ts`/`e2e-worker.ts`) to pass a
single-entry registry for `scan.analyze.v1`; runtime behavior for that topic
is unchanged. Added an integration test proving the generalization directly:
a non-analysis-topic row naming a canceled scan as its aggregate is
dispatched normally (not skipped), a row naming an aggregate ID with no
owning table row at all is dispatched successfully (the FK is gone), and
`attempt_number` can be omitted. Verified locally: `lint`, `typecheck`,
`format:check --end-of-line auto`, `test` (403/403, unchanged count — no
tests moved suites), `test:integration` for `@vinylhound/database` (56/56,
+1 net new, run against a real Postgres migrated with the new file), and
`npm run build` (all workspaces). No ADR-0027 boundary changed: this task
operated entirely inside `scan`'s own schema, as ADR-0027's "Consequences"
section anticipated.

Exit: integration/failure tests cover crashes before/after publish and consumer
commit, duplicates/out-of-order delivery, key conflicts, poison events, restart,
and account deletion races. Prove one intended library/copy effect, preserved
original/model/prompt/review audit history, and no cross-service SQL. Rehearse
cutover/rollback with pending work in staging. The UI never reports a completed
save before the completion projection arrives.
