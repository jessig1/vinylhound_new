### Differences and limitations that cannot be hidden

- P3.5's workload contains no catalog/discovery request. In addition, the
  repository's development tier intentionally keeps discovery in-process, and
  the unmodified harness starts local web/worker processes rather than accepting
  a remote staging base URL. This sample therefore exercises the scan/core
  role/schema split and worker boundary, but cannot measure P4.1's discovery
  network hop or P4.3's delivery-repository split. Task 2's staging exercises
  and Task 3's deploy/cost evidence cover those boundaries.
- Migration 022 intentionally removed cross-schema user foreign keys. The old
  harness reset (`truncate users, albums cascade`) therefore no longer clears
  scan-owned rows between concurrency legs. Fresh random users keep the timing
  samples independent, and timing records come only from each leg's worker
  stdout, but `estimatedCostUsd` now accumulates across live legs. The report's
  first live value is $0.0146 and its second is $0.0293 cumulative, so the
  second leg is $0.0147 by subtraction. Recreating the dedicated database before
  the invocation restored the same clean starting state; no production or
  development data was touched. This is a harness limitation caused by the
  intentional FK removal, not evidence of an application-cost regression.
- The live baseline report did not persist model/detail identifiers. The
  current run used the project's configured `gpt-5.6-terra`/`high` inputs, the
  same configuration family documented around the P3.5 live sample, but exact
  equality cannot be proven from the old artifact. Provider service conditions
  also changed across the six-day interval. Total concurrency, fixture, scan
  count, and client-side application path are exact matches; Task 3 must treat
  live latency changes as provider variance unless corroborated elsewhere.
- The current commit necessarily includes all changes since P3.5, not only the
  extraction commits. Same-host deterministic-stub results are the application
  comparison; live-provider improvements cannot be attributed to extraction.

The exercises intentionally do **not** describe PostgreSQL as isolated: scan
and core have distinct roles and schemas, but share one physical PostgreSQL
deployment. Database outage, failover, connection exhaustion, or maintenance
therefore remains a shared failure boundary by design (ADR-0030), and neither
the worker-scale nor discovery-outage result changes that fact. Task 3 must
compare the operational cost of this boundary rather than infer a false
availability gain.
