# P5.1 subplan: improve album detection through measured iterations

Date: 2026-09-30. Status: D01 implemented and verified with synthetic footage;
D02-D12 remain open. See [D01 evidence and recording guide](../CAPTURE_DIAGNOSTICS_D01.md).
Parent: [P5.1 reliable hands-free capture](phase-5-capture-ai-discovery.md#p51--reliable-hands-free-capture).

## Outcome and scope

A person presents a record sleeve, the scanner selects that sleeve, captures
one usable image, and becomes ready for the next sleeve. It should work with
ordinary hand placement, varied artwork, and supported indoor backgrounds.
It must not treat a wall calendar, book, monitor, person, or inner artwork as
an accepted jacket capture.

The [September 30 video review](../CAPTURE_VIDEO_REVIEW_2026-09-30.md) establishes
the immediate problems: wrong-object outlines and guidance, missed visible
sleeves, and no successful scans reported across six distinct covers. The
earlier yellow-cover upload used the wrong inner boundary. Neither trial is
a formal recall measurement or clean raw-camera replay.

This subplan improves P5.1 Tasks 1-3's implemented pipeline before Task 4 can
pass. Their completed infrastructure is retained; the checkboxes do not imply
detector quality has passed. P5.2 remains the owner of private detector/device
evidence; P5.3 remains the owner of artist/title identification evaluation.
Each result is recorded once and linked from those milestones.

Public automatic capture remains default-off. Manual capture, user review,
idempotent uploads, and the source-image audit trail remain requirements.
The separate development-user database incident must be resolved for an
end-to-end trial, but must not contaminate local detector accuracy measurements.

## Architecture to iterate toward

Separate these decisions so a failure has a specific cause:

| Stage    | Question                                                    | Evidence/output                                                                   |
| -------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Propose  | Where might a sleeve be?                                    | Multiple regions, optional corners, geometric or model evidence, detector version |
| Select   | Which region is the presented object?                       | Selected target and why; relationships between outer and inner regions            |
| Track    | Is this the same presentation?                              | Target identity, visibility, motion, removal/replacement, reset reason            |
| Assess   | Is this image usable, and are its crop corners trustworthy? | Separate image-quality and crop-validity results; unknown values stay unknown     |
| Capture  | Is there enough current evidence for one capture?           | Frozen best frame, selected image path, one presentation event                    |
| Identify | Which release might this be?                                | Existing asynchronous AI/catalog candidate and user-review flow                   |

Keep browser media and inference in `apps/web/src/app/scan/camera/`, heavy
frame work in the bounded worker, and album identification in the existing
backend worker. Keep selection/tracking policies testable without a camera.
A geometric score is not an album probability; model scores require measured
thresholds and are not catalog facts. No new service is selected by this plan.

[ADR-0032](../decisions/0032-experimental-cover-candidate-capture.md) and
[ADR-0033](../decisions/0033-audited-analysis-crops.md) govern current behavior.
Revise the relevant decision before implementing a conflicting capture policy;
add an ADR before changes to providers, service boundaries, persistence, or
public contracts. Change contracts and add frozen fixtures before consumers.

## D01 — Explain every frame decision

**Deliverable:** opt-in local diagnostics plus a bounded private recording mode.

Work in `cover-detector.ts`, `cover-detector.worker.ts`, `cover-camera.ts`,
`cover-tracker.ts`, and a development-only diagnostic surface. Record source
frame ID/time/dimensions, preprocessing transform, app/detector/config version,
proposal geometry, rejection stage/reason, selection rationale, tracker reset,
capture event, and processing time. Keep image-quality values explicitly
unevaluated when earlier stages did not run.

Separate numeric traces from an explicit raw-frame export. Save frames before
guides or badges are rendered; use private local artifacts, no application
logging of image bytes and no automatic upload. Cap recording duration, bytes,
and queued writes; report dropped frames and timing gaps. Stop recording on
camera stop or session cancellation. Diagnostics are off during normal use.

**Done when:** a short local recording maps a visible decision back to its
frame and rejection stage; the recorder stops at its declared bounds; replay
metadata distinguishes missed input from a detector rejection. Camera stop,
manual capture, and worker failure release resources. Record timing overhead
with diagnostics on/off. Synthetic footage can verify the tooling; it does not
complete D02's real-camera baseline.

## D02 — Establish a repeatable failure baseline

**Deliverable:** private manifest/labels, local replay command, and sanitized
baseline report under `docs/`; tool code can live under `scripts/capture/`.

Collect raw webcam presentations that reproduce the supplied videos: yellow
border plus inner artwork, dark/glossy covers, fingers on edges, bright window,
and wall calendar/frames. The maintainer supplies consented recordings and
verifies labels; implementation supplies recording, labeling, and scoring tools.
Annotate presentation start/end, sleeve region/visible corners, actual clipping,
hand occlusion, eligible/challenging status, and no-album intervals. Missing
corners remain unknown; never manufacture ground truth behind a hand.

Initial development target: at least 20 eligible presentations across 10 covers and two
recording sessions, 10 direct replacements, 10 held-cover sequences, and two
minutes of varied no-album footage. This is a debugging set, not a release gate.
Retain every challenging case and report its denominator separately.
Reserve different covers, sessions, and backgrounds for a locked final set.
For a learned model, keep training, development validation, and final test
groups disjoint; adjacent frames must never cross those groups.

Replay the production detector/tracker with recorded timestamps and explicit
gap handling. Report proposals found, correct targets selected, captures per
presentation, wrong-object/inner crops, duplicates, replacements, rejection
counts, capture latency, and frame time. Score misses separately from latency
among successes. Verify one replay's event alignment against a live trace.

**Done when:** the labeled development target is available; rerunning the same
version/config on the same inputs reproduces decisions; a report identifies
which stages lose the presented sleeves. Mark missing recordings/labels as
pending. The two UI screen recordings remain qualitative evidence only.

## D03 — Separate detector proposals from capture policy

**Deliverable:** a local detector adapter and typed proposal/selection/quality
results consumed by one tracker and one replay runner.

Extract proposal generation from candidate ranking and capture qualification.
Support absent corners and absent semantic scores without inventing defaults.
Retain source coordinates and frame identity through each stage. Keep current
geometry as the reference adapter and preserve existing selection behavior
until D04. Define worker-message validation/version handling if its payload
changes; no malformed or stale result may authorize capture.

**Done when:** reference-adapter replay matches D02's decisions, coordinate
mapping survives resize/aspect changes, and alternative adapters can run on
identical inputs without changes to queueing, upload contracts, or tracking.
The worker still has one job in flight with bounded frame retention.

## D04 — Select the sleeve rather than the background

**Deliverable:** corrected ranking and nested-boundary association.

Replace global largest-area selection with measured evidence from guide
overlap, centrality, boundary support, and target continuity. Apply the
incomplete-outer-boundary veto only to a contained/associated inner proposal.
Use scene persistence or motion as supporting evidence, not proof of an album.
Reject ambiguous foreground targets without letting an unrelated clipped wall
object generate sleeve-specific instructions. Preserve protection against
capturing Blind Melon's inner artwork as the entire jacket.

**Done when:** regression cases demonstrate that a clipped wall object cannot
veto a separate viable sleeve, while an associated clipped sleeve still blocks
its inner-artwork crop. D02 reports improved correct-target selection for the
targeted failures with no new wrong-object captures on its negative footage.
Report cases with no sleeve proposal separately; selection cannot recover a
region that was never proposed. Verify the yellow/calendar setup physically.

## D05 — Give advice supported by the selected target

**Deliverable:** stage-specific, stable feedback in `capture-guidance.ts` and
`capture-session.tsx`.

Tie distance, clipping, tilt, and hold-steady feedback to the selected target
identity. Distinguish not found, blocked, not evaluated, and ready. Do not
display an unevaluated detail check as a measured focus problem. Expire advice
when its target disappears or is replaced. Make manual capture prominent after
prolonged searching without submitting a frame automatically as recovery.

**Done when:** the calendar cannot produce move-back advice about the yellow
sleeve; removal clears target-specific instructions; truly clipped sleeves
still get useful advice. A short physical trial and accessible browser checks
show matching outlines, instructions, and readiness state. This task may pass
without improved capture recall if the remaining limitation is accurately shown.

## D06 — Track one presentation through brief detection losses

**Deliverable:** measured temporal policy in `cover-tracker.ts` with reset reasons.

Use stable target association and a bounded visibility grace period. Retain
the best frozen frame and its matching geometry. Distinguish hand movement,
exposure changes, actual removal, and direct replacement. Choose grace,
stability, and replacement thresholds from development traces, then freeze
them before the next comparison. Do not let a stale target authorize a capture
after the sleeve has left or a different sleeve has entered.

**Done when:** replay covers short gaps, moving/held sleeves, direct swaps,
similar artwork, removal/reintroduction, and intentional second copies. It
improves targeted missed captures without adding duplicates, stale-frame
captures, or wrong-object captures on the development set. Capture latency is
reported alongside recall, including the number of misses. Verify ten sequential
presentations physically and record every extra action and failure.

## D07 — Compare an OpenCV boundary detector

**Deliverable:** an experimental adapter and a keep/replace/escalate report.

Compare the repaired TypeScript baseline with OpenCV contour/line proposals and
corner refinement through D03's interface. Freeze the common tracker, selection
policy, quality gates, and input set so algorithm effects can be distinguished
from policy changes. Use a declared finite experiment matrix, such as two input
sizes and at most two boundary configurations; include the existing 320px input.
Do not tune against the final held-out set. Measure cold load, asset size,
frame time, memory, corner accuracy, false captures, and presentation recall.

Freeze a development screen before running the matrix: at least 95% of the
eligible presentations captured (at least 19/20 for D02's initial corpus),
zero wrong-object or inner-artwork captures, zero false captures during its
two-minute negative interval, and zero duplicates in its ten hold sequences.
Report corner usefulness, replacement recall, and latency alongside these
counts; do not hide misses by reporting latency only. These small denominators
can reject a weak approach but cannot establish release reliability.

**Done when:** the comparison is reproducible and selects the simplest candidate
passing that development screen, or records the specific unmet criteria and
opens D08a. Development improvements justify device validation, not a release
claim. Stop adding geometry heuristics when the bounded comparison has failed;
document the failure rather than treating more tuning as completion.

## D08a — Decide whether a learned sleeve detector is feasible

**Conditional deliverable:** a model/data/runtime feasibility decision.

Enter only after D07 establishes the remaining geometry failures. Define the
learning target as locating a physical record sleeve across unfamiliar artwork,
with separate boundary estimation; do not train a classifier for each album
title. Inventory suitable weights, labels, redistribution rights, runtime/device
requirements, model/download size, and estimated experiment compute/cost.
Generic object labels or runtime availability are not evidence of sleeve recall.

`docs/PRODUCT.md` excludes training/fine-tuning before prompt/model baselines
are evaluated. Complete the applicable P5.3 baseline first or explicitly revise
that product scope through a documented decision before training. An existing
suitable model can be evaluated without representing it as newly trained.
Use the current manual/source flow to avoid a circular prerequisite.

**Done when:** choose an existing suitable model for evaluation, define a
permitted training experiment with data/scope prerequisites satisfied, or record
that no viable model/data option exists. Record the model/runtime decision and
any required ADR before integration. Do not claim a dataset is sufficient or
promise a training duration without evidence.

## D08b — Run one bounded learned-detector experiment

**Conditional deliverable:** versioned model artifact and a comparison report,
or a documented failed experiment.

Implement the selected model behind D03's adapter. If training is required,
label outer sleeves and include hands, frames, calendars, screens, books,
glare, minimalist artwork, and inner rectangles as challenging examples or
negatives. Freeze dataset splits, compute budget, trial count, evaluation
metrics, and stop criteria before the run. Calibrate operating thresholds on
development validation only. Keep model/config/checksum provenance and measure
the complete browser path, including preprocessing and startup.

**Done when:** the comparison with D07 reports capture recall, wrong targets,
false captures, duplicates, useful crops, latency, and device cost at the chosen
operating point. Select a candidate only if its gains satisfy the predeclared
criteria without relaxing the safety/quality gates. If it fails, identify the
data or model limitation and record a next experiment; public capture stays off.

## D09 — Decide image usability separately from crop confidence

**Deliverable:** a capture-policy decision with offline evidence and a required
ADR update before any change to ADR-0033's automatic-crop behavior.

Use the selected detector to evaluate blur/detail, coverage, partial hand
occlusion, and clipping for the actual target. Keep image usability distinct
from reliable perspective corners. Evaluate three explicit outcomes: capture
with validated crop, retain a source-only candidate where justified, or request
manual recovery. A source-only automatic path requires reliable sleeve evidence;
stillness or an arbitrary rectangle is insufficient. Unknown corners must not
be synthesized into apparently valid provenance.

**Done when:** the decision retains strict crops or defines exact conditions
and provenance for a source-only fallback. Report fallback frequency, false
captures, and usable-image outcomes. Use P5.3's paired source/crop comparison
before claiming identification gains. A fallback cannot count as a successful
crop or silently reduce the crop-gate denominator. Design any contract/schema
change and its old/new fixtures before D10 implementation.

## D10 — Integrate the selected policy with audited uploads

**Deliverable:** one reviewed capture-to-upload path matching D09's decision.

Keep the accepted source, frame timestamp, detector/config identity, geometry
when applicable, and the preview's relationship to the image used for analysis
traceable. Determine which provenance already exists and add only missing fields
through the proper contracts/persistence owners and ADR. Preserve short-lived
signed uploads, server validation, and the existing idempotency identity through
retry, refresh, quota pauses, and batch rollover. Do not silently replace a
declared invalid/missing crop with a source fallback during completion.

**Done when:** integration checks prove the chosen bytes reach analysis, their
source relationship remains auditable, retries create no extra scan, and old
manual/file/multi-view flows remain compatible. Show the actual capture path
honestly in preview/privacy copy. Run contract compatibility and relevant
database/storage tests if those boundaries changed.

## D11 — Verify responsiveness and the complete scanning path

**Deliverable:** physical-device compatibility/performance report and a working
ten-album development session using the selected pipeline.

Measure cold start, warm p50/p95 detection/capture timing, peak/steady memory,
frame backlog, and a ten-minute session on the slowest intended device. Preserve
one inference job in flight, bounded source-frame retention, and the current
20-item/32-MiB admission limits unless an explicit measured revision is made.
Handle worker/model load failure, stop during inference/encoding, tab hiding,
camera switching, permission loss, and unavailable acceleration with manual
recovery. Diagnose any runtime selection using actual device evidence.

Before scoring end-to-end results, prove manual capture can provision its user,
upload, submit, analyze, and reach review in the intended environment. Resolve
the database incident through that preflight; record its errors separately from
detector misses. Use the synthetic worker for routine non-billable integration
checks and P5.3's controlled configuration for live recognition comparisons.

**Done when:** the report includes physical webcam, iPhone Safari, and Android
Chrome outcomes or explicitly unsupported/pending setups; no synthetic browser
profile substitutes for a device. The development ten-album session completes
without per-album shutter/submit actions on each proposed supported setup,
and pause/retry/manual recovery work. Missing devices remain pending.

## D12 — Evaluate and decide rollout per setup

**Deliverable:** completed [gate sheets](../CAPTURE_GATE_EVALUATION.md), P5.2 and
P5.3 evidence links, and a release-or-remain-off decision.

Freeze detector/model/configuration and consume the locked held-out set once.
Use the existing per-setup gates: zero false captures in ten negative minutes;
at least 95/100 eligible captures across 20 covers; warm capture median at most
1s and p95 at most 1.5s; zero duplicates in 100 hold sequences; at least 95/100
replacements and 95/100 useful accepted crops; ten-album hands-free completion;
bounded responsive operation; and the P5.3 source/crop identification decision.
Report source-only paths separately if D09 introduced them. Define any extra
usable-image gate before evaluation; do not weaken existing gates retroactively.

**Done when:** every claimed supported setup has a recorded decision and its
actual counts. A failed evaluation can complete this decision task, but keeps
P5.1 Task 4 open and public capture disabled. A passing setup also needs a
reviewed enablement/rollback plan; if setup-specific enablement is unavailable,
implement that control before exposing automatic mode to unqualified setups.
If results drive further tuning, the consumed test data becomes development
evidence and a fresh held-out evaluation is required.

## How to run each iteration

Use one behavioral hypothesis per implementation change. Before editing, record
the baseline commit, configuration, private dataset version, targeted failure,
and expected measurable result. After editing, run the same development replay,
inspect the affected physical presentation, and decide **keep, revise, or revert**.
An increase in capture count is not an improvement if it introduces wall-object
captures, inner crops, or duplicates. Do not repeatedly tune on held-out results.

Record this compact experiment entry in the task's linked report:

| Field                | Required record                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| Task / hypothesis    | One behavior being changed and why                                                                           |
| Reproduction         | Private manifest/version, frame or presentation IDs, device/setup                                            |
| Baseline / candidate | Commits, detector/model/config versions, preprocessing                                                       |
| Before / after       | Correct targets, captures/presentations, false captures/minutes, wrong crops, duplicates, replacement counts |
| Timing / resources   | Latency with success count, misses, frame p95, startup and memory where affected                             |
| Human check          | Correct outer sleeve, guidance, crop/source usefulness                                                       |
| Decision             | Keep/revise/revert, remaining failure, next task                                                             |
| Verification         | Relevant automated checks and physical evidence; explicitly pending items                                    |

Run `npm run check` before each implementation handoff and `npm run build` for
application changes. Add focused policy tests and relevant browser/integration
coverage for the changed risk. Private replay evaluates detector accuracy;
synthetic tests evaluate invariants. Run the broader browser/device matrix at
D11/D12 or when a cross-browser regression justifies it. Update task status,
linked evidence, and `docs/HANDOFF.md` after every iteration.
